# 企业经营分析沙盒 MVP 设计规格

> 版本：V0.1  
> 日期：2026-07-28  
> 状态：设计已确认，待实施计划  
> 依托项目：AI Native Starter

## 1. 产品定义

### 1.1 暂定名称

- 英文：Enterprise Analytics Sandbox
- 中文：企业经营分析沙盒

### 1.2 一句话定位

为 AI+BI 和经营分析 Agent 生成账实一致、异常可控、答案可验证的企业经营环境。

### 1.3 核心产品任务

产品不以“生成大量模拟数据”为最终目标，而是帮助用户完成一次可复现、可判分的
经营分析 Agent 测试：

```text
创建经营考试
→ 选择异常场景
→ 生成并下载考试包
→ 使用待测 Agent 分析
→ 提交 Agent 答案
→ 对照 Ground Truth 评分
→ 输出能力评测报告
```

数据生成是底层能力，用户真正获得的是一套“企业经营分析考试”。

### 1.4 首批目标用户

- AI+BI 产品经理；
- 数据分析 Agent 开发者；
- 企业 AI 团队；
- Text-to-SQL、归因分析和报告生成产品的测试人员。

SaaS 通用测试人员、高校教师和业务终端用户不作为 V0.1 核心用户。

### 1.5 需要解决的问题

- 真实经营数据敏感，难以用于外部开发和演示；
- 团队缺少具有完整业务逻辑的测试数据；
- 现有 Mock 数据只有表结构，缺乏跨流程一致性；
- Agent 给出结论后缺少标准答案；
- 模型、Prompt 和工具升级后缺少稳定回归测试；
- 不同 Agent 无法在相同环境下进行可比评价。

### 1.6 V0.1 验证命题

用户能否在 30 分钟内创建一套制造企业经营场景，并客观判断自己的分析 Agent
有没有发现异常、找对原因、引用正确证据和遵守判断边界。

## 2. MVP 范围

### 2.1 包含

- 一个简化制造企业模型；
- 销售、采购、库存和财务四个业务域；
- 12 个月时序数据；
- 15 张核心数据表；
- 5 个预置经营异常场景；
- SQLite、CSV、数据字典和指标语义层；
- 每个场景的 Ground Truth、标准 SQL 和评分规则；
- Agent 答案提交；
- 确定性评分、模型辅助提取和人工复核；
- 场景工坊、考试库、考试详情和评测报告四个一级页面。

### 2.2 不包含

- 通用合成数据平台；
- 用户真实数据上传、脱敏或生产数据拟合；
- 多行业模板；
- 完整 ERP、MRP 和复杂 BOM；
- 增值税、汇率、折旧、薪酬和复杂制造费用分摊；
- 模型训练和微调；
- 第一版直接接入用户 Agent；
- 多租户、SSO 和企业级权限；
- 可视化拖拽规则；
- 百万级或压力测试数据；
- 法律意义上的“完全合规”承诺。

## 3. 用户旅程与页面

### 3.1 用户旅程

1. 用户创建经营考试，选择企业规模、数据期间、数据量和难度；
2. 用户选择一个主要异常场景；
3. 系统生成经营环境并完成一致性校验；
4. 用户下载公开考试包；
5. 用户将数据交给自己的分析 Agent；
6. 用户粘贴或上传 Agent 分析结果；
7. 系统将答案提取为统一结构；
8. 系统对照 Ground Truth 评分；
9. 有歧义的结论进入人工复核；
10. 系统输出评测报告和改进建议。

### 3.2 页面

| 页面 | 核心任务 |
|---|---|
| 场景工坊 | 创建考试并选择异常 |
| 考试库 | 查看、筛选和复用历史场景 |
| 考试详情 | 下载数据、查看任务、提交答案 |
| 评测报告 | 查看分数、事实差距、幻觉与改进建议 |

### 3.3 考试包公开边界

| 内容 | 对待测 Agent 公开 |
|---|---:|
| SQLite 数据库与 CSV | 是 |
| 数据字典与表关系 | 是 |
| 指标定义和分析任务 | 是 |
| 预埋异常与真实原因 | 否 |
| 标准 SQL 与正确证据 | 否 |
| 具体评分答案 | 否 |

第一版不连接用户 Agent。用户下载考试包，并以 JSON、Markdown、HTML 或纯文本
提交 Agent 结果。非结构化内容由答案提取器转换为统一结构。

## 4. 企业数据模型

### 4.1 生成原则

系统不分别随机生成业务表、凭证和报表。所有数据遵循：

```text
企业与主数据
→ 正常经营参数
→ 业务事件
→ 业务单据与库存流水
→ 复式记账凭证
→ 科目余额与财务报表
```

业务事件是唯一事实源。异常通过改变经营过程参数产生，不允许直接篡改最终报表
数字制造异常。

### 4.2 主数据

| 表 | 内容 |
|---|---|
| `dim_organization` | 公司、事业部、工厂、销售区域 |
| `dim_customer` | 客户、行业、区域、等级、信用期 |
| `dim_supplier` | 供应商、供应品类、账期 |
| `dim_product` | 产品、产品线、标准成本、销售价格 |
| `dim_account` | 会计科目、科目类型、报表归属 |

### 4.3 销售流程

| 表 | 业务节点 |
|---|---|
| `fact_sales_order` | 销售订单 |
| `fact_sales_delivery` | 销售发货 |
| `fact_sales_invoice` | 销售开票与收入确认 |
| `fact_cash_receipt` | 客户回款 |

### 4.4 采购流程

| 表 | 业务节点 |
|---|---|
| `fact_purchase_order` | 采购订单 |
| `fact_goods_receipt` | 采购入库 |
| `fact_supplier_invoice` | 供应商发票 |
| `fact_cash_payment` | 供应商付款 |

### 4.5 库存与财务

| 表 | 内容 |
|---|---|
| `fact_inventory_movement` | 入库、出库、退货与调整流水 |
| `fact_journal_entry` | 行级会计凭证及业务来源 |

利润表、资产负债表、现金流量表、科目余额表、应收和应付余额均从凭证和业务流水
推导，不作为独立随机事实表。

### 4.6 基础记账规则

销售发货：

```text
借：主营业务成本
贷：库存商品
```

销售开票与收入确认：

```text
借：应收账款
贷：主营业务收入
```

客户回款：

```text
借：银行存款
贷：应收账款
```

采购入库：

```text
借：原材料
贷：应付暂估
```

收到供应商发票：

```text
借：应付暂估
贷：应付账款
```

供应商付款：

```text
借：应付账款
贷：银行存款
```

## 5. 数据一致性要求

每次生成必须自动验证：

1. 每张凭证借贷平衡；
2. 资产等于负债与所有者权益之和；
3. 期末库存等于期初库存加采购入库减销售出库及调整；
4. 期末应收等于期初应收加销售发票减客户回款；
5. 期末应付等于期初应付加供应商发票减供应商付款；
6. 银行余额与现金收支一致；
7. 收入、成本和毛利能够追溯到产品和订单；
8. 所有主外键有效；
9. 单据日期顺序合理；
10. 相同版本与随机种子生成完全相同的数据。

错误分三级：

- 阻断错误：借贷不平、外键失效、非预期负库存、日期倒置；
- 质量警告：分布过度集中、数据量不足或异常不够明显；
- 场景失效：目标异常未达到设计幅度，或出现计划外重大异常。

阻断错误和场景失效不得发布。生成器最多使用派生随机种子重试三次，仍失败则
返回明确错误，不交付问题数据包。

## 6. 首发异常场景

### 6.1 增收不增利

- 表象：收入增长 18%，销量增长 22%，利润下降 12%；
- 原因：低毛利产品占比上升、重点客户折扣增加、原材料价格上涨；
- 考察：价格、销量、产品结构和成本拆解，以及相关性和因果边界。

### 6.2 原材料涨价侵蚀毛利

- 表象：收入和销量稳定，毛利率持续下降；
- 原因：核心材料采购单价上涨、售价未同步调整、成本传导存在时间差；
- 考察：销售、采购、库存与成本穿透分析。

### 6.3 销量增长但库存积压

- 表象：销量增长，库存和周转天数同时恶化；
- 原因：增长集中于少数产品，其他产品仍按原预测补货；
- 考察：产品结构分析和“畅销缺货、滞销积压”并存识别。

### 6.4 收入正常但现金恶化

- 表象：收入和利润达标，经营现金流下降，应收账龄上升；
- 原因：重点客户账期延长、逾期比例上升、月末集中确认收入；
- 考察：利润与现金区分、正常账期与逾期区分。

### 6.5 订单增长但交付能力下降

- 表象：新增订单增长，发货率下降，延迟交付上升；
- 原因：特定材料延期导致相关产品缺货，其他产品正常；
- 考察：订单、采购、库存和交付证据链，以及局部问题与整体问题区分。

每个场景只设置一个主要经营问题，可包含多个共同解释该问题的原因。

## 7. Ground Truth

每个场景保存：

```yaml
ground_truth:
  observations: 应当识别的异常
  root_causes: 数据能够证明的原因
  contributions: 原因影响程度
  evidence: 支撑结论的表、字段和数值
  unknowns: 仅凭数据不能判断的事项
  forbidden_claims: 与数据矛盾或没有依据的说法
```

系统不使用单篇“标准报告”进行文字相似度评分。不同表达只要能映射到相同 Cause ID
并获得正确数据支持，就视为语义一致。

## 8. Agent 答案与评分

### 8.1 标准答案结构

推荐用户提交：

```json
{
  "anomalies": [
    {
      "metric": "gross_margin_rate",
      "direction": "down",
      "magnitude": -0.046
    }
  ],
  "causes": [
    {
      "cause": "raw_material_price_increase",
      "confidence": 0.91,
      "evidence": [
        {
          "table": "fact_goods_receipt",
          "field": "unit_price",
          "value": 128.5
        }
      ]
    }
  ],
  "unknowns": [
    "客户折扣是否属于主动竞争策略"
  ],
  "recommendations": []
}
```

### 8.2 三层评价

1. 确定性评分：校验数字、方向、指标、数据字段、Cause ID、证据与禁止结论；
2. 模型辅助：从报告中提取结构化答案，完成语义映射和假设/事实识别；
3. 人工复核：处理新归因、语义歧义、临界评分和用户异议。

模型负责理解答案，程序负责核验事实，人工负责处理新知识与争议。

### 8.3 评分权重

| 维度 | 权重 | 评分方式 |
|---|---:|---|
| 异常识别 | 20% | 确定性 |
| 数字与指标 | 20% | 确定性 |
| 归因命中 | 25% | 确定性与语义映射 |
| 证据有效性 | 20% | 确定性 |
| 判断边界 | 10% | 规则与模型辅助 |
| 行动建议 | 5% | 模型辅助 |

行动建议权重保持较低，因为 V0.1 首先验证事实、原因和证据。

## 9. 系统组件

### 9.1 场景规格生成器

将企业规模、期间、随机种子、异常场景和难度转换为统一
`scenario_spec.yaml`。

### 9.2 Ground Truth 引擎

在数据生成前定义观察、原因、贡献、证据、未知事项和禁止结论，遵循“先有答案，
再生成数据”。

### 9.3 经营事件模拟引擎

按月推进销售需求、订单、发货、库存、采购、开票、收付款和月末结账状态。

### 9.4 单据与会计引擎

将经营事件确定性地转换为业务单据、库存流水、应收应付、现金收付、凭证和报表。

### 9.5 一致性验证器

执行阻断校验、质量校验和场景有效性校验。

### 9.6 考试包生成器

生成公开数据、Schema、语义层和任务说明，同时保证 Ground Truth 不进入公开包。

### 9.7 评测引擎

执行答案提取、事实核验、原因映射、边界判断、综合评分和改进建议生成。

## 10. AI 与规则的分工

| 能力 | 规则程序 | 大模型 |
|---|---:|---:|
| 数据生成与主外键 | 主责 | 辅助配置 |
| 业务事件推演 | 主责 | 不直接决定 |
| 会计凭证与报表 | 完全负责 | 不参与计算 |
| 异常注入 | 参数和规则 | 辅助场景描述 |
| Ground Truth | 结构化规则 | 辅助解释 |
| 非结构化答案提取 | 格式校验 | 主责 |
| 数字与证据评分 | 完全负责 | 不参与事实认定 |
| 语义等价判断 | Cause ID | 辅助 |
| 改进建议 | 提供事实 | 主责 |

可计算的事情不用大模型，可解释的事情才使用大模型。

## 11. 版本与审计

每套考试保存：

- 数据生成器版本；
- 场景版本；
- 指标版本；
- 评分规则版本；
- 答案提取模型与 Prompt 版本；
- 随机种子；
- 生成和校验记录。

新归因不得立即判错。系统将其标记为待复核原因；确认后可更新场景新版本，但历史
考试继续使用原评分规则。

## 12. 测试策略

### 12.1 单元测试

- 订单、发货、采购、库存、开票和收付款规则；
- 复式记账；
- 指标计算；
- 异常注入；
- Cause ID 评分。

### 12.2 属性测试

批量使用不同随机种子，持续验证借贷平衡、库存可解释、财务恒等式成立以及相同
种子可复现。

### 12.3 黄金场景测试

每个场景固定一套标准数据、正确答案、错误答案和幻觉答案。版本升级后确保：

- 正确答案分数稳定；
- 错误答案能够被识别；
- 幻觉答案不能获得高分。

## 13. MVP 验收标准

### 13.1 产品

- 用户 10 分钟内完成场景创建；
- 数据生成不超过 3 分钟；
- 数据包可直接用于 SQLite、Excel 和 Power BI；
- 用户不阅读技术实现文档也能理解任务；
- 评测报告至少给出一项具体可执行改进。

### 13.2 数据

- 15 张核心表关系完整；
- 10 项一致性校验全部通过；
- 相同版本与种子可复现；
- 5 个异常场景均有可验证 Ground Truth；
- 关键财务数字 100% 由事件和凭证推导。

### 13.3 需求验证

邀请 10 至 20 名目标用户：

- 至少 10 人完成一次完整测试；
- 至少 5 人用于真实 Agent 或 BI 开发；
- 至少 3 人在两周内重复使用；
- 至少 3 人愿意付费或推动团队采购；
- 平均数据准备时间相比手工方式下降 70% 以上。

达到以上标准只能证明初步需求，不直接等同于获得 PMF。

## 14. 开发顺序

1. 建立数据模型、业务事件模型和会计验证器；
2. 实现“增收不增利”黄金场景；
3. 输出 SQLite、CSV、指标与 Ground Truth；
4. 使用现有 AI 经营分析同事跑通一次；
5. 实现答案提交与确定性评分；
6. 增加剩余 4 个场景；
7. 最后实现四个产品页面。

第一阶段的完整成功标准是：一场考试能够稳定生成、完成作答并被可靠判分，而不是
先建成一个管理大量考试的平台。
